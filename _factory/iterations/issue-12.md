## Iteration 3 — Backend Reliability: defensive null-guard in init() with named-element error

- Critique: Every `document.getElementById(...)` call in `init()` returned `null` when an element was absent, but the result was immediately cast `as HTMLElement` — silencing TypeScript's null check. At runtime this would throw a cryptic `TypeError: Cannot set properties of null (setting 'maxLength')` several lines after the bad lookup, giving no indication of which element ID was missing. For a controller that documents a specific eight-element HTML contract, the failure mode should be an explicit, early error naming the offending ID so the developer knows exactly what to fix.
- Change: Extracted a private `requireElement<T>(id)` helper that wraps `getElementById`, checks for null, and throws `Error: init(): required element #<id> was not found in the document.` if the element is absent. All seven element lookups in `init()` now go through `requireElement` instead of the raw cast. Added a describe block "dom — init() null-guard: missing required elements" with one test per element ID (7 tests total), each confirming that removing that element from the fixture before calling `init()` throws an error whose message contains `#<id>`. Also documented the destroy()/cleanup tradeoff in the `init()` JSDoc: for this single-init demo the complexity of an AbortController pattern is not warranted, but the right approach for a long-lived SPA component is noted inline.
- Files touched: `frontend/lib/main.ts`, `frontend/tests/dom.test.ts`
- Tests: 106 passed before → 113 passed after (7 new tests added, 0 broken)

## Iteration 2 — UX/Product Polish: add ARIA live region and accessible labels to controller elements

- Critique: `#error-slot` had no ARIA live region, so validation errors were visually displayed but completely silent to screen readers — a user navigating by keyboard would hear no announcement when "Invalid format" appeared. `#sign-toggle` exposed only the raw "±" glyph as its accessible name; AT behaviour on that character varies (some say "plus-minus sign", some skip it). `#fahrenheit-output` and `#kelvin-output` were anonymous `<p>` elements with no label connecting them to the "Fahrenheit" / "Kelvin" concept when navigated out of reading order.
- Change: In `init()`, immediately after setting `input.maxLength`, four `setAttribute` calls were added: `errorSlot.setAttribute("role", "alert")` so errors are announced as live-region assertions; `signToggle.setAttribute("aria-label", "Toggle sign")` for an unambiguous button label; `fahrenheitOutput.setAttribute("aria-label", "Fahrenheit")` and `kelvinOutput.setAttribute("aria-label", "Kelvin")` so the output paragraphs are identifiable by AT. Four matching tests were added under a new describe block "dom — accessibility: ARIA attributes".
- Files touched: `frontend/lib/main.ts`, `frontend/tests/dom.test.ts`
- Tests: 102 passed before → 106 passed after (4 new tests added, 0 broken)

## Iteration 1 — Security Hardening: enforce maxLength on input to match parser length cap

- Critique: `convert.ts` exports `MAX_LENGTH = 32` and its JSDoc explicitly states it is "re-exported for callers who want to apply the same length cap in their own validation pass (e.g. to set a maxLength attribute on an `<input>`)." `lib/main.ts` never used it. A user could paste an arbitrarily long string (e.g. 100 000 characters) into `#celsius-input`; the browser would pass the full string to `parseTemperature()`, which would reject it correctly at the `s.length > MAX_LENGTH` guard, but the string would still traverse the trim and length-check code on every keystroke. The DOM attribute is the correct first line of defence: it prevents oversized input from entering the pipeline at all rather than relying solely on the parser's server-side-style guard. No `innerHTML` or injection risk was found; all DOM writes consistently use `.textContent`.
- Change: Added `MAX_LENGTH` to the import from `./convert` in `lib/main.ts`; added `input.maxLength = MAX_LENGTH;` immediately after element references are resolved in `init()`, so the browser enforces the 32-character cap natively. Added two tests in `tests/dom.test.ts` (describe block "dom — input maxLength enforcement") verifying the attribute is set and that it equals the parser's constant.
- Files touched: `frontend/lib/main.ts`, `frontend/tests/dom.test.ts`
- Tests: 100 passed before → 102 passed after (2 new tests added, 0 broken)
