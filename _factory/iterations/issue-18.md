## Iteration 3 — Backend Reliability: _readArtefact throws instead of calling process.exit(); run() returns boolean; env-var path overrides

- Critique: `_readArtefact` called `process.exit(1)` directly when a file could not be opened. This is the single most dangerous reliability pattern in a Node CLI-as-library: `run()` is exported and required by the test suite. Any future test that calls `run()` directly (rather than via `spawnSync`) when a required file is absent would silently kill the entire Vitest process — not just fail the test case. The issue is invisible until it happens, and when it does the diagnostic is confusing ("test runner exited with code 1, no failure recorded"). Additionally, `run()` itself called `process.exit(0)` and `process.exit(1)` inside its body, making the function non-reentrant and impossible to call safely from test harnesses or composition contexts. The file-path constants were also hardcoded to `__dirname`-relative values with no override mechanism, making it impossible to test the "missing file" code path without renaming real fixture files.
- Change: Three coordinated changes: (1) `_readArtefact` now throws `new Error(...)` instead of calling `process.exit(1)` — it is now a safe library function. (2) `run()` catches `_readArtefact` errors and returns `false` on file-not-found, removing all `process.exit()` calls from the function body; its return type is `boolean` (true = all passed). (3) The CLI entry point (`if (require.main === module)`) translates the boolean to `process.exit(run() ? 0 : 1)` — the only remaining `process.exit` call is at the process boundary where it belongs. Additionally: file paths now respect `CHECK_SECURITY_HTML` and `CHECK_SECURITY_HEADERS` environment-variable overrides (falling back to `__dirname`-relative defaults), enabling precise CLI-level missing-file tests without touching the source tree. `_readArtefact` is exported for unit testing. 7 new tests added: 4 unit tests for `_readArtefact` (reads file, throws on missing, message includes path, message includes prefix) and 3 CLI-level tests via `spawnSync` with env-var overrides (exit 1 on missing HTML, stderr message on missing HTML, exit 1 on missing headers).
- Files touched:
  - `frontend/scripts/check-security.js` — `_readArtefact` throws instead of exits; `run()` returns boolean; `process.exit` moved to entry point only; `CHECK_SECURITY_HTML` / `CHECK_SECURITY_HEADERS` env-var overrides; `_readArtefact` exported; stale duplicate JSDoc removed
  - `frontend/test/check-security.test.ts` — `_readArtefact` and `os`/`fs` imports added; 4 new `_readArtefact` unit tests; 3 new `run() missing artefact resilience` CLI tests using env-var path injection
- Tests: 165 passed / 0 failed before; 172 passed / 0 failed after

## Iteration 2 — UX/Product Polish: per-check progress output, summary counts, and --help flag

- Critique: The CLI had two DX problems. (1) On success, `run()` printed a single opaque line — `[check-security] All checks passed ✓` — giving developers no visibility into which checks ran. A developer could not tell from the output whether 1 or 5 checks executed, which undermines trust in the CI gate. (2) There was no `--help` flag; running `node scripts/check-security.js --help` produced an error. A developer onboarding to the project had to read the source to understand what checks existed and what the exit-code contract was.
- Change: Refactored `run()` to use a named-check table (`{ name, fn }` pairs) and print each check's pass/fail result as it runs (e.g. `  ✓  no-inline-styles`). The final summary line now shows counts: `5/5 checks passed` on success or `3/5 checks passed, 2 failed:` on failure, followed by the name-prefixed error messages. Added a `--help` / `-h` handler at the entry point that prints usage, lists all 5 check names with one-line descriptions, and documents the exit-code contract. Added 7 new Vitest tests (CLI output describe block) using `spawnSync` to assert on actual process output: --help exit code, --help usage line, --help check enumeration, --help exit-code docs, run() 5/5 summary, run() tick count, run() check name listing.

## Iteration 1 — Security Hardening: tighten SRI hash validation to reject malformed integrity values

- Critique: `_assertSRIAttributes` in `scripts/check-security.js` only checked that the `integrity` attribute started with the string `"sha384-"`. It did not validate the base64 payload that follows the prefix. An `integrity="sha384-"` (empty hash), `integrity="sha384-abc"` (too short), or `integrity="sha384-AAAA...="` (wrong alphabet) all silently passed the CI gate. A sha384 digest is 48 bytes, which encodes to exactly 64 standard-base64 characters (`[A-Za-z0-9+/]`) with no padding (48 % 3 === 0). The old `startsWith` check provided a false sense of security — the gate said "SRI is configured correctly" even for hashes the browser would reject. The bug was already present in `dist/index.html`: the JS bundle placeholder hash was only 62 characters long, which the old check silently accepted.
- Change: Replaced the `integrity.startsWith('sha384-')` test with a strict regex `SHA384_INTEGRITY_RE = /^sha384-[A-Za-z0-9+/]{64}$/`. Updated the error message to explain the correct format and provide the `openssl` command to generate a valid hash. Fixed the malformed 62-character placeholder hash in `dist/index.html` (extended to 64 chars). Added 4 new Vitest tests covering: empty hash (`sha384-`), too-short hash (`sha384-abc`), padding character present (`=` in final position), and a correctly-formed 64-char hash.
- Files touched:
  - `frontend/scripts/check-security.js` — `_assertSRIAttributes` + new `SHA384_INTEGRITY_RE` constant
  - `frontend/dist/index.html` — corrected JS bundle placeholder hash from 62 to 64 chars
  - `frontend/test/check-security.test.ts` — 4 new tests for the stricter validation
- Tests: 154 passed / 0 failed before; 158 passed / 0 failed after
