## Pass 3 — Backend Reliability: idempotent cleanup and zombie-timer guard

- Critique: `mountTemperatureWidget` was not safe against two reliability failure modes. (1) **Double-unmount**: calling the returned cleanup function twice would attempt to remove the same event listener and clear an already-null timer on the second call — harmless in practice, but not idempotent by contract, leaving callers (React StrictMode, test afterEach + explicit cleanup) with no safety guarantee. (2) **Zombie debounce timer**: if a debounce timer was armed (e.g. by a valid keystroke) and then the widget was unmounted before the 400 ms window elapsed, the timer callback would fire after unmount and write `textContent` into the now-detached (orphaned) SR elements. The detached nodes were kept alive by the closure until the timer fired — a memory leak. More seriously, in a double-mount scenario where the caller forgot to call the first cleanup before mounting again, the first widget's zombie timer would fire against the orphaned elements and silently produce the wrong text. Because `container.innerHTML` was replaced by the second mount, both SR element references pointed at different objects, so the writes were actually no-ops in the DOM — but the correctness guarantee was fragile and undocumented.
- Change: Introduced an `unmounted: boolean` flag inside the closure, initialised to `false`. The cleanup function now (a) returns early if `unmounted` is already `true` (idempotent), and (b) sets `unmounted = true` before cancelling the timer and removing the listener. Both debounce timer callbacks (`valid` and `invalid` branches) now check `if (unmounted) return` as their first statement, self-defusing any timer that outlives its widget. Added three targeted tests to `frontend/tests/a11y.test.ts`: double-unmount does not throw, zombie timer after cleanup does not mutate the DOM, and double-mount leaves the second widget's SR region uncontaminated by the first widget's abandoned timer.
- Files touched: `frontend/lib/temperature-widget.ts`, `frontend/tests/a11y.test.ts`
- Tests: 65 passed before → 68 passed after (3 new reliability tests added, 0 regressions)

## Pass 2 — UX/Product Polish: remove redundant aria-live attributes and add mobile input hygiene

- Critique: Three issues were present in the widget markup. (1) `role="status"` on `#temp-result` and `#sr-result` already implies `aria-live="polite"` per the ARIA spec; the explicit `aria-live="polite"` attribute was therefore redundant and risks double-announcement in some assistive technologies. (2) `role="alert"` on `#sr-error` already implies `aria-live="assertive"`; same problem. (3) The `#temp-error` visible paragraph carried `aria-live="assertive"` with no `role`; because error announcements are already delegated to the dedicated `#sr-error` live region, the `aria-live` on the visible paragraph was extraneous and would cause duplicate announcements on each invalid keystroke. (4) The input lacked `autocapitalize="none"` and `spellcheck="false"`, meaning mobile virtual keyboards would autocapitalise the first character and underline decimal/numeric input with red squiggles — confusing feedback for a temperature field.
- Change: Removed the now-redundant explicit `aria-live` attributes from `#temp-result`, `#sr-result`, `#sr-error`, and `#temp-error`, relying solely on the implicit live-region semantics carried by `role="status"` and `role="alert"`. Added `autocapitalize="none"` and `spellcheck="false"` to the `<input>` element. Updated the module JSDoc to document the rationale.
- Files touched: `frontend/lib/temperature-widget.ts`
- Tests: 65 passed before, 65 passed after (no regressions)

## Pass 1 — Security Hardening: enforce maxlength on temperature input

- Critique: The widget accepted arbitrarily long strings from the browser. `parseTemperature` rejects inputs over 32 chars at parse-time (`MAX_LENGTH = 32`), but the `<input>` element carried no `maxlength` attribute, so the browser would buffer and hand the full string (however long) to the event handler before the parser's length guard fired. The `convert.ts` source explicitly exports `MAX_LENGTH` and its JSDoc calls out this exact use case ("e.g. to set a maxLength attribute on an <input>"), making the missing attribute a documented gap. This is a defence-in-depth issue: a 100 000-character paste would traverse the DOM event pipeline and call `parseTemperature` unnecessarily.
- Change: Imported `MAX_LENGTH` from `./convert` in `temperature-widget.ts` and interpolated it as `maxlength="${MAX_LENGTH}"` on the `<input>` element. The browser now rejects characters beyond position 32 before the `input` event fires, making the widget's first line of defence the DOM itself rather than the parser.

- Tests: 65 passed before, 65 passed after (no regressions)
